# AGENTS.md

This file provides guidance to Codex (Codex.ai/code) when working with code in this repository.

## Project Overview

**AudioLib Explorer** is a high-performance desktop audio library management tool for sound designers. It manages 1M+ WAV audio files with sub-500ms search latency using SQLite FTS5 full-text search.

**Current Phase**: Rust desktop implementation. Legacy Python source and its test scripts have been removed; previous committed versions preserve that history. The original database and local YAML configuration remain read-only migration inputs.

## Rust Workflow (Primary)

The current implementation is the Cargo workspace at the repository root. See `doc/Rust_Architecture.md` for its contracts and `doc/Rust_Validation.md` for actual verification results. Python architecture examples in retained design specifications are historical guidance; do not use SQLAlchemy ORM, tkinter, PyQt6, or Alembic for new Rust functionality.

- Rust 1.97.1 MSVC, Slint 1.17.1, rusqlite 0.40.2 with bundled SQLite FTS5.
- `crates/audiolib-core`: owned domain DTOs, DataProvider, validation and settings.
- `crates/audiolib-db`: versioned SQLite migration, search, folder hierarchy, Metadata editing and cancellable scanning.
- `crates/audiolib-audio`: streaming decode, resampling, CPAL playback and Waveform caches.
- `crates/audiolib-windows`: x64 ASIO driver identity and Windows path integration.
- `crates/audiolib-ipc`: bounded local named-pipe playback control; local-only, never a network listener.
- `crates/audiolib-remote`: blocking HTTP client for server mode (snapshot sync, WebDAV playback cache, DPAPI-protected secrets); see `doc/Rust_Remote_Mode.md`.
- `server/audiolib-server`: axum library server for server mode; its HTTP contract is `doc/api/README.md`.
- `app/audiolib-desktop` / `app/audiolib-cli`: GUI and CLI adapters.

Use the smallest validation scope that covers the changed behavior, following the development checks below. Ordinary GitHub-hosted CI only checks formatting; all functional tests run locally. Use full workspace checks only for broad changes or uncertain impact. Development and release validation both select affected packages, direct consumers and actual shipped features; publishing a new tag alone does not expand the test scope. For ASIO builds, dot-source `tools/prepare-asio.ps1`, then enable the ASIO feature on the selected packages. The preparation script pins and verifies Steinberg SDK 2.3.4; never let the dependency build download an implicit SDK.

Windows client release: `tools/build-release.ps1` builds only the desktop/CLI binaries; portable packaging: `tools/package-portable.ps1 -SkipBuild`. Server releases use `tools/build-server-release.ps1` and their platform packager. Packaging and `validate-portable.ps1` read the release EXEs from `$env:CARGO_TARGET_DIR` when it is set (else `<repository root>/target`); run the tools with `pwsh` (PowerShell 7) where possible. Routine outputs replace `dist/latest/portable` and `dist/latest/AudioLibExplorer-latest-win-x64-portable.zip`. The fixed local installation is `<repository root>/local_release/`; update it using the mandatory workflow below. Keep runtime state in `%LOCALAPPDATA%/AudioLibExplorer/v1`, separate from binaries. Tests use temporary directories and must not modify the legacy database or WAV assets.

Prefer `tools/release-pipeline.ps1` for tagged local delivery: preview with `-Tag <tag>`, then explicitly `-Action Run`; use the matching native plan and actual shipped configuration. The Windows client plan includes accepted-payload installation through `install-local-release.ps1`. See [Release pipeline](doc/Rust_Release_Pipeline.md). Choose source checks/regressions by risk with `-ChecksFile`; omitted source checks are `not-requested`, never passed. Repeat the same Run to resume after input/environment/artifact identity checks, not to restart every suite. Use `-Action Status` for the short saved snapshot or `-Action Logs -Stage <id> -Tail 15` for failure diagnostics. Do not dump full logs, file manifests or historical reports into tool output; retain them as private evidence and report the concise result/path. Wait on the existing long-running tool session in 30–60 second intervals instead of issuing a new command per stage. This pipeline does not authorize publication or replace platform/data-safety acceptance.

End each successful task that actually built/tested Rust with budgeted maintenance of owned caches: `tools/clean-build-artifacts.ps1 -Action Run` applies a 40 GiB debug-cache budget while retaining release outputs; omit Action for preview. Prefer `check-local.ps1 -CleanBuildArtifacts` or the same switch on the release pipeline (`-BuildCacheLimitGiB` adjusts the limit); application delivery cleanup follows packaging, acceptance and installation. Do not also add cleanup inside pipeline source checks or prune repeatedly mid-task. Failed tasks retain diagnostic caches by default. Pure documentation tasks and unchanged reused results do not trigger another scan. Use `Incremental` for lighter pruning; `All -MaxGiB 0` is explicit post-delivery full profile cleanup. Never remove SDKs, Cargo/Rustup home, dist, installations, formal tooling, working libraries or source audio. External caches require verified explicit registration, not an inferred claim; keep unverified historical caches. Managed builds/tests and cleanup coordinate through a shared/exclusive build lease; an active compiler or target executable blocks cleanup without process termination. Report logical space estimates, blocked/unverified maintenance and unmet budget limits. See [Build cache maintenance](doc/Rust_Build_Cache.md).

Run subsystem validation scripts only when their behavior is affected, as described below. Real Windows ACL tests must remain within a verified owned temporary subtree and restore permissions in finally. The million-record performance runner is `cargo run --release --locked -p audiolib-db --bin search-benchmark -- --records 1000000 --queries 100`; use it for relevant performance changes or an explicit performance acceptance request.

Windows server-package acceptance uses `search-benchmark` to create its owned fixture. When running that acceptance, build the helper explicitly with `cargo build -p audiolib-db --bin search-benchmark --release --locked`; ordinary client/server release builds do not need benchmark binaries.

For local application delivery, after packaging run `tools/validate-portable.ps1` against `dist/latest/portable` once for EXE identity, isolated first startup, CLI/UI and startup diagnostic checks. The optional hosted release verifier checks published asset metadata and SHA256 only.

Changes to scan coordination, configuration persistence or Metadata writes require the relevant data-safety regressions, including `tools/validate-review-fixes.ps1` for affected cross-process or release behavior. Labels, layout and unrelated configuration fields do not trigger that entire suite. Scanning must acquire the per-database OS lock; leave its sidecar file in place after unlocking to avoid file-replacement races. Bind GUI drafts to the displayed file ID and an edit revision, keep saves ordered, and drain requested writes before closing.

Library management uses schema v8 and the owned contracts in `audiolib-core/src/library.rs`; server snapshots support schema 3 through 8 with full format/feature validation. Older snapshots are validated and any required derived-state upgrades run only in an owned copy. Run `tools/validate-library-management.ps1` when changing the behavior or storage of backup/restore, relink/removal, import/export, scan history or multi-library operations; text or layout changes alone do not require it. Restore and maintenance must validate an owned snapshot, create a rollback backup, drain GUI writes and scans, and invalidate old reader/UI generations. An unrelated SQLite file must never replace a library. All removal operations are database-only; never delete a source WAV. See `doc/Rust_Library_Management.md` for the delivered workflow.

Ordinary CLI commands must validate existing libraries and must not create an explicit or missing non-default library; use `db create` or `db import`. Maintenance/restore must exclude all cross-instance writes through the administration lease, including single-record Metadata and playback history, while scans still permit ordinary annotations. Restore adapts page size only in its owned staging copy. Resolve and validate the real WAV target before relinking. Protect shared preferences with the desktop instance lease before database initialization. Playback history distinguishes successful play sessions from load generations: Stop/Ended followed by Play starts a new session, while pause/resume, seek, transform changes and repeat retain the session.

All business data accesses go through DataProvider and return owned values. SQL values must be parameterized; sort fields must be allowlisted. GUI updates return to the Slint event loop. Audio callbacks must not perform application file I/O, database work, logging, allocations or blocking synchronization. Handle cancellation and stale requests explicitly. Preserve all existing library Metadata and user annotations when importing and rescanning.

Document Rust `unsafe` safety invariants and keep FFI narrow. Add a source path comment at the start of each Rust module and document public interfaces. Continue using the terminology in Technical_Architecture.md Appendix A and the performance target **P95 latency <500ms for 1M+ records**.

## Development checks by change scope

- Documentation and process-rule changes: inspect the diff, links and command examples; run `git diff --check`. Do not run Cargo, application regressions, benchmarks, rebuilds or installation for unchanged binaries.
- Workflow/validation-script changes: check YAML/PowerShell syntax and affected command routing or smoke commands locally. These changes alone do not require rebuilding or reinstalling unchanged application binaries.
- Rust behavior changes: run `cargo fmt --all -- --check` once, strict Clippy for affected packages (for example `cargo clippy -p audiolib-db --all-targets --locked -- -D warnings`), and tests covering the changed behavior. Prefer an existing test target such as `cargo test -p audiolib-db --test search_fragments --locked`; use package-wide tests when the behavior cannot be scoped reliably. Changes to a public contract also require relevant direct-consumer checks.
- UI text, layout and resources: compile the affected application and inspect the changed interaction or view. A successful Clippy or required release build already supplies compilation evidence; do not add a separate `cargo check` for the same purpose. Add behavior tests only for a meaningful state or interaction regression, not to assert literal strings, coordinates or source-code structure.
- Shared dependencies, toolchain/application build configuration, broad refactors or uncertain impact: expand locally to `cargo clippy --workspace --all-targets --locked -- -D warnings` and `cargo test --workspace --all-targets --locked`. `tools/check-local.ps1 -Package <packages>` runs format, strict Clippy and tests for the selected packages once; omit `-Package` only for a deliberate workspace-wide check; `-Asio` enables the release ASIO features for that same pass, after verified SDK preparation. This is an explicit full-check entry point, not a routine command for every small task.
- During development, run ASIO checks only for affected audio/device backends, ASIO feature wiring or SDK/dependency changes. Use the selected feature configuration; unrelated UI, database or server changes do not require repeating every test with ASIO. Release builds still use the verified SDK and the selected packaging features.

For affected Windows client packages, use `tools/check-local.ps1 -Package audiolib-desktop,audiolib-cli -Asio` or narrower existing test commands. Server-only changes use `-Package audiolib-server -NoDefaultFeatures` with the native target and do not trigger client/audio-backend tests. Do not first run the non-ASIO suite or append another ASIO pass. Check non-ASIO conditional code only when affected by the change, using targeted package/tests; a deliberately non-ASIO release uses `check-local.ps1` without the switch. Real ASIO device acceptance is needed only for affected driver/backend behavior and requires the relevant hardware.

GitHub-hosted checks are deliberately minimal: ordinary CI uses one Linux job for `cargo fmt` on relevant `main`, `beta` and `codex/**` pushes and all PRs. Pure documentation/screenshot pushes are skipped; every PR reports the required `Linux (fmt)` check. CI runs no Rust tests, Clippy, ASIO matrix or extra platform jobs. `.github/workflows/release.yml` is an optional manual, read-only check of published release identity, exact asset names and SHA256; it never builds or packages. Portable UI/CLI smoke, server startup/health, package privacy and synthetic package regressions all run locally. The compatibility entry point `tools/ci-release.ps1 -Tag <tag>` manually builds/packages the Windows client and writes a `not-run` runtime report; use it instead of separately invoking build/package, never as an additional test stage. Before creating a release tag, complete checks for the actual changed behavior and shipped configuration, relevant subsystem regressions and local packaged-startup acceptance, reusing still-valid results. Do not rerun every package on every platform merely because they share a release version. Run platform-specific server/database regressions on matching local hosts when those paths change; record unavailable platform/hardware coverage explicitly.

Select additional checks by the actual risk, not by every subsystem mentioned in a task:

| Affected behavior | Additional validation |
| --- | --- |
| Schema, migration, restore, maintenance leases, library identity, import/export or relinking | Relevant database integration tests; `validate-library-management.ps1` for changed library operations and release CLI behavior |
| Scan coordination, configuration persistence, Metadata write ordering or shutdown draining | Relevant scan/desktop regressions; `validate-review-fixes.ps1` for cross-process/data-preservation behavior, `validate-desktop-close.ps1` for affected close behavior |
| Permission denial, scan enumeration or missing-file reconciliation | `validate-access-denial.ps1`; retain temporary ACL isolation and restoration |
| Legacy import or WAV Metadata decoding | Relevant migration/decoder tests; `validate-runtime.ps1` when the real fixture is available |
| Playback, transport or IPC | Relevant audio/IPC tests; `validate-playback-ipc.ps1` when changing real playback or cross-process control |
| Waveform, spectral rendering, redraw or search performance | The relevant visual or performance check; million-record/real-library benchmarks only for performance-sensitive changes or requested acceptance |
| Packaging, release identity, licenses or publication privacy | Run synthetic package boundary regressions and portable/server-package startup checks locally for the affected payload; hosted verification checks published asset metadata and checksums only |

Do not remove data-safety coverage to shorten a high-risk task. Keep existing formal tests and scripts; reduce when and how broadly they run. Add a regression test when it can catch a plausible failure, not to meet a test-count or coverage quota. Missing hardware or legacy fixtures must be reported as unverified, without repeated attempts at unchanged conditions.

Reuse passing results while the relevant application/test source, features, toolchain and environment remain unchanged; a tag or documentation change alone does not invalidate Cargo results. After a fix, rerun the failed check and checks affected by that fix; do not restart unrelated passing suites. Build/package each payload once and run its packaged acceptance once. A passing package-wide test already includes its targeted tests; do not run both consecutively unless a later change invalidates the result. Run synthetic packaging regressions only when their scripts/rules change. Mac releases use `package-macos-client.ps1 -ValidateRuntime` to combine structural and native acceptance; do not append the standalone validator for those unchanged artifacts. Final release payloads must still be built from the final main/tag identity and accepted as those actual payloads. Do not routinely hash the entire source tree or a large working database at every stage; use isolated fixtures and checks appropriate to the operation. Report the scope actually verified and any remaining acceptance limit. See [Testing Strategy](doc/Testing_Strategy.md) for stage responsibilities and examples; historical results in `doc/Rust_Validation.md` are evidence, not an every-task checklist.

## Mandatory local application delivery and release installation

`local_release/` is the persistent local installation used for manual acceptance and everyday use. Reuse this exact directory; do not create versioned or timestamped local installation directories. `dist/latest/` remains the packaging output, and `target/` remains the build output. Neither replaces the required local installation step.

For every completed change affecting the application, follow this sequence:

1. Complete the checks selected by change scope above, plus the applicable data-safety regressions. Do not add unrelated workspace/ASIO suites. Keep test databases in isolated temporary directories.
2. Build the latest source with `tools/build-release.ps1`, then package with `tools/package-portable.ps1 -SkipBuild`; for a tagged package, `tools/ci-release.ps1 -Tag <tag>` replaces those two commands. Use the same ASIO selection for build and packaging; the default includes the verified ASIO SDK. Build/package each payload once. Never install stale binaries from an earlier build.
3. Run `tools/validate-portable.ps1 -BinaryDirectory dist/latest/portable` (isolated synthetic data by default; `-CleanCheckout` remains a compatible alias). Use `-LegacyImport` only for affected legacy-import acceptance with its fixture available. If built and packaged with `-WithoutAsio`, pass the same switch to validation; ASIO licenses remain required by default. License preflight runs during packaging and before runtime acceptance. Only proceed after successful build, packaging and validation.
4. Gracefully close any application instance using `local_release/`, allowing requested Metadata writes and scans to drain. If files remain locked, report the blocker instead of forcing termination or claiming installation succeeded. Create `local_release/` if absent, then overwrite its application files with the validated portable payload: both EXEs, launcher, packaged documentation, resources, example configuration and licenses. Copy only package-owned files; do not delete or mirror-purge the installation directory or overwrite local runtime data. Verify resolved destinations stay within this repository's `local_release/` before any cleanup.
5. Verify SHA256 identity of installed package-owned files, including both EXEs, against the validated package. Confirm the installed CLI version and one desktop startup using an owned temporary `AUDIOLIB_DATA_DIR` with explicit isolated settings so startup cannot discover the working/legacy library. Restore the normal environment afterward. The full portable suite already passed in step 3; repeat it against `local_release` only if installation identity/startup fails or the installation behavior itself changed. Use `local_release/Start-AudioLibExplorer.cmd` for subsequent manual acceptance and normal launches.
6. Report the build/version or source commit, validation results and fixed installation path. A successful build alone does not complete an application development task; the local installation must also be updated and verified. Documentation-only changes do not require rebuilding or reinstalling unchanged binaries.

### Persistent local database and settings

- Keep the working database, `settings.json`, logs and caches on this machine at `%LOCALAPPDATA%/AudioLibExplorer/v1`; preserve any existing explicit `AUDIOLIB_DATA_DIR` and configured library paths. Do not relocate or recreate an existing library merely to install a build. Program files in `local_release/` and persistent data have separate lifecycles.
- Every local upgrade must retain all libraries, Metadata, annotations, scan history and preferences. Never copy an empty, fixture, CI or packaged database over the working library, and never delete SQLite sidecars as installation cleanup. Use the supported backup/restore workflow when data migration or recovery is needed.
- Restore the user's normal data-directory environment after isolated validation. Daily GUI/CLI use must continue to select the same local data directory and active library across builds.
- Keep `/local_release/` ignored by Git. Do not upload local databases, preferences, logs or caches as release assets; publish only the clean portable package from `dist/latest/`.

### Published release synchronization

After a requested GitHub Release has been successfully published, update and verify the same `local_release/` installation before declaring the release task complete. Install the published portable payload, or a local payload whose hashes match that release; verify the installed version and EXE hashes against the published artifact. Do not assume an unrelated local build is identical to a package built elsewhere. For a downloaded artifact, verify its published archive checksum and validate the extracted payload once with `tools/validate-portable.ps1 -BinaryDirectory <extracted-payload> -CleanCheckout -PublishedReleaseReport <report> -ExpectedTag <tag> -ExpectedCommit <commit>`; this mode uses the published report's EXE hashes instead of unrelated local build outputs. Then use the installation identity/startup checks above without repeating the full portable suite. Preserve the local data described above throughout the update. Report remote publication and local installation status separately if either step is blocked. This synchronization rule does not authorize publishing a release unless the user requested publication.

## Performance targets and terminology

| Metric | Target | Context |
|--------|--------|---------|
| Search latency (P95) | <500ms | 1M+ records |
| Search latency (P50) | <100ms | 1M+ records |
| Playback start | <50ms | Button click to actual audio output |
| UI response | <100ms | User interactions |
| Scan throughput | >100 files/sec | Metadata extraction on SSD |

Use **Waveform**, **Metadata**, **FTS5** and **DAW** consistently. State the primary metric as **P95 latency <500ms for 1M+ records**. Report actual benchmark conditions and hardware measurements separately from these targets; driver-reported latency is not button-to-output measurement.

Validate user inputs through Rust core contracts, bind SQL values, validate real file targets against configured scan roots, and cap search queries at 500 characters. Chinese indexing uses jieba-rs with the shared audio terminology dictionary. Preserve unknown extension Metadata and user annotations during migration and rescanning. Playlist/project-reference data is retained, while new editors, DAW parsers and plugins remain deferred; hide unimplemented entry points. Server mode exists through `audiolib-remote` and `server/audiolib-server`: v1 clients open a validated read-only snapshot, refuse library writes, never touch the local working library, and never log or export the token or WebDAV password.

## Git Workflow
### Beta flow
- `beta` is the integration branch. Feature/fix PRs target `beta`; `main` only receives merges from `beta` (or hotfix branches) after beta testing passes. Both branches are protected: PR required (0 approvals), required check `Linux (fmt)`, no force push or deletion; admins are not enforced so release operations still work.
- Beta pre-releases are tagged `vX.Y.Z-beta.N` on `beta` (X.Y.Z = `Cargo.toml` version) and published as GitHub pre-releases (`check-release.ps1`, `ci-release.ps1`, `package-server.ps1` accept the suffix; suffixed tags are always `--prerelease`).
- Release naming: tag `vX.Y.Z` → title `AudioLib Explorer vX.Y.Z` (not prerelease); tag `vX.Y.Z-beta.N` → title `AudioLib Explorer vX.Y.Z-beta.N`, prerelease. Title, tag and `Cargo.toml` version (ignoring the suffix) must agree. Create releases with `tools/release-create.sh <tag>`, which derives the title from the tag; verify with `tools/check-release.ps1 -Tag <tag> -CheckGitHubRelease` (mismatch = hard error).
- Release assets: from 0.8.4 onward, each Release ships six archives (Windows x64 client, macOS arm64 client, macOS arm64 server, Linux x64 server, Docker linux/amd64 and linux/arm64 offline images), each with a `.sha256` (twelve assets). Version 0.8.3 retains three packages/six assets; releases through 0.8.2 retain two packages/four assets. Mac desktop uses manual installation/update with native signing/startup acceptance; ad-hoc is not Apple notarization. Docker images consume validated public Linux packages, disable in-container binary updates and are replaced as images. From 0.8.5 (first included version) a native Windows x64 server ZIP `AudioLibServer-<tag>-win-x64.zip` is added (seven archives, fourteen assets; see doc/Rust_Windows_Server_Release.md); earlier versions and source builds remain available. Standalone Linux arm64 server archives are not published; arm64 Linux payloads are internal Docker inputs.
- Install a beta side by side with `tools/install-beta.ps1 [-Destination <dir>]` (default `beta_release/` under the checkout, ignored by Git). It never touches `local_release/` and adds `AudioLibExplorer-beta.cmd`, which sets `AUDIOLIB_DATA_DIR` to `%LOCALAPPDATA%/AudioLibExplorer/beta` (override with `AUDIOLIB_BETA_DATA_DIR`) so beta never shares data with stable `v1`. Always launch beta through that script.
- Before promoting `beta` to `main`, follow [Beta testing flow](#beta-testing-flow).

### Beta testing flow
Application candidates use the automated refresh and smoke checks below. Select any additional UI validation from this version's actual changes and risks; a historical GUI checklist is not a default release gate. Documentation/process-only updates follow [Development checks by change scope](#development-checks-by-change-scope): reuse relevant passing evidence instead of rebuilding unchanged binaries or rerunning unrelated checks. Preserve the original source and binary identities of reused results; do not describe them as newly executed. Required checks must pass before promotion. Branch, tag and version rules are in [doc/Rust_Versioning.md](doc/Rust_Versioning.md) and the Beta flow above; do not restate them here. Never commit server addresses or tokens: use `<beta-server>` placeholders or the env vars below.

1. **Refresh the beta server** (Mac, `tools/beta-refresh.sh`): deploys the `beta` head to the beta server instance and checks its own result (served commit equals the `beta` head, `/health` is `ok`). This is the Mac-side check; there is no separate server smoke script.
   - Usage (on the Mac, after `. ~/bin/audiolib-dev-env.sh`): `BETA_APP_DIR=<beta app dir> BETA_DATA_DIR=<beta data dir> SERVICE_NAME=<beta launchd label> WORK_DIR=<tmp dir on the build volume> tools/beta-refresh.sh [--with-db] [--no-build <binary>]`; optional `PORT` (default 8791), `ROOT_PROBE_SECS` (default 15), `BETA_WAIT_SECS` (positive integer, default 1800), `PROD_DB` (required with `--with-db`, opened read-only).
   - Steps: build `origin/beta` in a detached worktree under `WORK_DIR`; with `--with-db`, copy the production library with SQLite online backup, `quick_check` it and reset `library_id` (drops `<db>.server-state.json`); swap only `bin/audiolib-server` through `server/deploy/redeploy-server.sh` (backup + automatic rollback), never the launcher, which holds the macOS file-access grants; check `/health` is `ok` and `commit` equals the `beta` head; then read 4 KiB from one file under every configured root.
   - Startup wait includes schema/search migrations. Increase `BETA_WAIT_SECS` before refreshing a large library if needed (for example `BETA_WAIT_SECS=3600`); timeout still fails the gate. Only when structured health confirms an ongoing database migration and the candidate's explicit expected commit, binary version and API/schema conditions match, retain the new binary/update markers and backups without another restart; this remains FAIL, never acceptance. Other failures retain normal rollback behavior. Binary rollback does not downgrade a migrated database: returning to an older schema-incompatible binary also requires its matching database backup.
   - Root probe failing with no answer means the launcher lacks the network/removable volume permission (System Settings > Privacy & Security > Files and Folders) or the disk is asleep; a person must grant it on the Mac, then rerun. Never point the script at the production instance.
   - Log: `$WORK_DIR/beta-refresh-<timestamp>.log` (build output in `$WORK_DIR/beta-build.log`, DB clones in `$WORK_DIR/beta-backups/`); exit code 0 means every check passed.
2. **Client smoke test** (Windows, `tools/beta-smoke.ps1`), from the beta install:
   `powershell -NoProfile -ExecutionPolicy Bypass -File tools/beta-smoke.ps1 -BaseUrl $env:AUDIOLIB_BETA_URL -ExpectedCommit <beta head short sha> -MinEntries <expected library size> -ReleaseDir <beta install dir> -ExpectedExeSha256 <SHA256 of the built AudioLibExplorer.exe>`
   - Parameters: `-BaseUrl` (required, or `AUDIOLIB_BETA_URL`), `-ExpectedCommit` (must match `/health.commit`), `-Token` (only when the server requires one), `-ReleaseDir` (CLI location; with it the full `AudioLibCli remote sync --force` runs by default, `-NoSync` skips it, `-Sync` is accepted for compatibility), `-MinEntries` (synced entry count must reach the minimum and equal the server's `/library` count), `-ExpectedExeSha256` / `-ExpectedHashFile` (expected SHA256 of `AudioLibExplorer.exe`; without either, `AudioLibExplorer.exe.sha256` next to the EXE is used; a mismatch or no expected value is a FAIL; `AudioLibCli.exe` is compared with `AudioLibCli.exe.sha256` when present), `-StreamSamples` (default 20), `-StreamTimeoutSec` (per-track timeout, default 15; all samples are always tried), `-SyncTimeoutSec` (default 900), `-KeepSyncData`.
   - Checks (read-only GET/HEAD; never starts, stops or scans anything): health/version/commit; unauthenticated access (200 for LAN peers in the default `external` auth mode, otherwise 401 + `WWW-Authenticate: Bearer`, doc/api §2.2); `/waveforms/bundle` 200 with a quoted ETag, then 304 for HEAD and GET with `If-None-Match`; `Range: bytes=0-4095` reads of random present records under configured roots on `/audio/{id}/stream` (206, `audio/*`, RIFF/RF64 magic); sync (default with `-ReleaseDir`); EXE SHA256 against the expected value.
   - Log: `%TEMP%\audiolib-beta-smoke-<timestamp>\beta-smoke.log` (plus `sync.out.txt`/`sync.err.txt`); the path is printed at the end.
3. **UI validation when affected**: select relevant interaction or visual checks for the UI behavior changed in this version. Use applicable behavior tests, isolated startup and visual inspection; request a person's observation only when a specific remaining UI risk needs it. Versions without related UI changes do not require manual GUI confirmation, and unrelated historical checks must not be repeatedly presented to the user. When a beta GUI launch is needed, use `AudioLibExplorer-beta.cmd`.

**Pass/fail**: each script prints a PASS/FAIL table; exit code 0 means every check passed, anything else is a failure. If human observation is needed for a current UI risk, report it as passed only after it is observed. Unscored UI guidance or historical GUI reminders printed by a script do not add release gates.

**Recovering from a failure**: read the log, fix on a branch off `beta` and merge by PR (never force-push), then rerun the flow from step 1. Commit mismatch: rerun the refresh. Stream 503 `ROOT_OFFLINE`/timeouts: the NAS root may be waking; check `/roots` and rerun. Sync failure: inspect `sync.err.txt`; rerun with `-KeepSyncData` to keep the temp data dir. Do not start/stop servers or kill a running client to "fix" a run.

**Data dir safety**: the stable data dir `%LOCALAPPDATA%\AudioLibExplorer\v1` is never read or written by beta tooling. `beta-smoke.ps1` refuses to run when `AUDIOLIB_DATA_DIR` ends in `\v1` and syncs only into a fresh dir under `%TEMP%` (deleted afterwards unless `-KeepSyncData`), so the beta dir `%LOCALAPPDATA%\AudioLibExplorer\beta` used by the GUI is not touched either.
